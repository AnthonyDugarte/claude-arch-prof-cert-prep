## Attacks that landed

### A. The control hierarchy and the heuristics built on it

**[BLOCKER] §2.1 (five-layer hierarchy) vs. §3 T1 (bypass-resistance row) — the ranking contradicts itself and mis-ranks deterministic controls.**
§2.1 orders "strongest to weakest containment": removal (1) → human gate (2) → classifier (3) → programmatic validation (4) → prompt (5). T1's own table then rates *Programmatic validation* "High for what it checks" and *Classifier* "Medium — a second model can also be fooled." The ordered list and the table disagree about positions 3 and 4.
*Counter-scenario:* an agent must never initiate a payment to an address outside a pre-approved beneficiary list. A candidate who memorized §2.1 picks "add an LLM classifier that screens payment destinations" over "enforce the beneficiary allow-list in code," because the list says classifiers are stronger. That is the wrong answer in practice and on any item contrasting a model-based screen with a deterministic predicate — the classifier is itself promptable and has a false-negative rate; the allow-list does not.
*Second counter-scenario:* the hierarchy puts the human gate at #2, above deterministic validation. On a high-volume flow the chapter's own anti-patterns section admits reviewers rubber-stamp ("Reviewers approve nearly everything flagged," §5). A gate with a measured 98% approve rate is empirically a weaker control than an allow-list that cannot be talked into a new payee.
*Required fix:* replace the single ranking with **two axes** and say so explicitly: **bypass resistance** (deterministic code and architectural removal are highest; classifiers and humans are probabilistic; prompts are lowest) and **coverage/expressiveness** (humans and classifiers can judge fuzzy things no predicate can express; code and removal only cover what you can specify). The correct decision rule is: *express the constraint deterministically if it can be expressed; use a classifier or a human only for the residue that cannot.* Then reconcile T1 to match.

**[BLOCKER] §7 heuristic 1 and §2.1 — "remove the capability whenever removal is possible" has the wrong boundary condition.**
"Possible" is not the test. The guide's Sample 1 works because the stem states "support staff only ever need to read tickets and draft replies" — i.e. *the capability is not required by the role*. The chapter's heuristic drops that predicate.
*Counter-scenario:* an item states that support agents resolve ~20% of tickets with a goodwill credit and the business requires same-call resolution. Removal is still "possible" (route to a back-office team) but it destroys the use case; the correct answer is scoped authority — a $50 per-transaction cap, per-agent daily budget, one credit per ticket, idempotency key, and a gate above the cap. A candidate drilled on "removal is possible → remove" picks the option that breaks the requirement, which is exactly the "looks-responsible-but-wrong" trap this exam is built on.
*Required fix:* restate as **"Remove the capability when the role's actual task does not require it. When it does, the move is narrowing authority (scope, cap, rate, tenancy, credential), not removing the tool and not logging it."** Add the narrowing vocabulary to T1 as a sixth column; right now T1 has no cell for "capability needed but authority narrowed," which is the most common real answer.

**[MAJOR] §2.1 / §7 heuristic 3 — "a prompt instruction is never the complete answer for a material risk" has no carve-out for constraints no other layer can express.**
*Counter-scenario:* legal has approved a scope statement ("the assistant must not give tax advice; it may describe published policy"). There is no schema check, allow-list, or range check for "is this tax advice." The only layers available are a hardened system prompt, a classifier (also a model), and an eval set that measures scope adherence. An item whose key is "harden the system prompt with the approved scope statement and add a scope-adherence eval to the release gate" will be rejected by a candidate who has learned to eliminate any option containing the words "system prompt." Note that "Design system prompts, templates, and guardrails" is a *Domain 2 objective* — a blanket anti-prompt reflex costs items in two domains.
*Required fix:* qualify to **"a prompt instruction is never *sufficient on its own* for a material risk"** and add the boundary: *where the constraint is fuzzy and admits no deterministic predicate, prompt + classifier + measured eval + blast-radius limits is the whole available answer; the correct option then adds a measurement and a containment layer, not a replacement for the prompt.*

**[MAJOR] §7 heuristic 4 / §2.4 / T4 — "irreversible + high-impact → synchronous human gate" omits the move that dominates it: make the action reversible.**
*Counter-scenario 1:* a card-fraud system must freeze a card within ~1 second or the fraud completes. Freezing is high-impact and not instantly reversible for the cardholder. A synchronous human gate guarantees the harm. The correct architecture is automate the action + build a fast, self-service reversal path + post-hoc review of the reversal rate. The chapter mentions "reversible-by-default design" once, buried as a compensating control in §2.2, and never as the thing to try **before** reaching for a human.
*Counter-scenario 2:* a document-deletion tool. The exam-correct move is a staged state — soft-delete with a 30-day restore window — which converts an irreversible action into a reversible one and makes the gate unnecessary. A candidate taught the heuristic picks "require an admin to approve every deletion," adding latency and a fatigue surface to a problem that had a cheaper structural answer.
*Counter-scenario 3:* a gate nobody can staff. The chapter's tiers assume reviewer availability; a "synchronous approval" control on a 24/7 workflow with business-hours reviewers is a queue, not a control, and on an item that mentions global operating hours it is the wrong answer.
*Required fix:* reorder the rule to **"irreversible + high-impact → first try to make it reversible (staged/pending state, undo window, two-phase commit, claw-back, delayed execution); gate with a human only for the residue that cannot be made reversible, and only where a reviewer is actually available within the action's latency budget."** Add "reversibility is a design choice, not a fixed property of the action" as an explicit concept in §2.4 — it is the single highest-value idea missing from this chapter.

**[MAJOR] T1 discriminator — "A human gate whenever the action is irreversible or high-impact, *regardless of the other layers*" is an absolute a competent architect can defeat.**
*Counter-scenario:* a refund tool constrained in code to (a) the exact amount of a verified prior charge, (b) to the original payment instrument, (c) once per order, (d) within 90 days. The action is financially material and not trivially reversible, yet there is no discretionary decision left for a human to make. A gate here adds latency and manufactures a rubber-stamp. The deterministic control has *substituted* for the gate by removing the judgment.
*Required fix:* **"A human gate is required when the decision contains judgment that cannot be reduced to a deterministic predicate. When the parameters of the action can be fully constrained in code, the deterministic control substitutes for the gate."** Also delete "regardless of the other layers" — it contradicts the chapter's own defense-in-depth framing.

**[MAJOR] §2.2 / T2 — "detective alone never suffices" is over-generalized, and T2's "Preventive: often sufficient [regulatorily] alone" contradicts §2.2 on the same page.**
§2.2 correctly says an EU AI Act high-risk conformity file expects logging **and** a separate human-oversight mechanism. T2's table then rates preventive controls "Often sufficient if well-designed" for "Regulatory sufficiency alone." Both cannot be true.
*Counter-scenario:* an item asks "the team removed the capability that caused the incident; what does the high-risk conformity file still require?" A candidate taught "preventive is often sufficient" answers "nothing further"; the correct answer includes record-keeping/logging, human oversight, and post-market monitoring as *separately mandated* obligations.
*Second attack on the same pair:* there is a class of risk where detection **is** the primary control because there is nothing to gate — model/prompt drift, emergent disparate impact, degradation of a retrieval index, misuse of legitimately granted access. The chapter's blanket "monitoring is not a mitigation" trains a candidate to eliminate the correct option on a drift item.
*Required fix:* (1) change T2's preventive cell to "Never sufficient alone where logging, human oversight, or post-market monitoring are independently mandated." (2) Qualify §2.2 to **"detective controls are never sufficient alone for an action whose harm is irreversible; they are the *primary* control for slow-onset risks (drift, bias, degradation, insider misuse) where no discrete action exists to gate."**

**[MINOR] §7 heuristic 6 — "'Compliant because we use Claude' is *always* wrong" is a strawman that can misfire.**
No real option is phrased that badly. The risk is the over-generalized reflex: a candidate learns to distrust any option that credits vendor posture, then hesitates on Item 2's own key (BAA + org-level HIPAA readiness + eligible features) which *is* substantially a vendor-configuration answer.
*Required fix:* restate as **"vendor posture (BAA, DPA, authorized boundary, certifications) is necessary and never sufficient — the correct option names both the vendor instrument and the customer-side design obligation."**

### B. Compliance overreach and legal-flavored claims

**[MAJOR] §4 Scenario 3 — "CUI requires the FedRAMP High + IL4/5 boundary" conflates a civilian federal agency with a DoD mission, and the chapter teaches the conflation as a heuristic (§7 heuristic 7).**
The stem is "a federal agency" with CUI-level policy documents. DoD Impact Levels come from the DoD cloud framework and apply to DoD missions; a civilian agency's control baseline is set by its own FIPS-199 categorization, which for much CUI lands at FedRAMP **Moderate**, not High, and does not invoke an Impact Level at all.
*Counter-scenario:* an item describes a civilian agency, CUI, and a FedRAMP **Moderate** authorization requirement, with options including a Moderate-authorized surface and the agency's existing authorized boundary. A candidate drilled on "CUI ⇒ IL4/5 ⇒ Bedrock GovCloud" over-specifies, picks GovCloud, and misses the key.
*Also missing from the scenario:* the gating artifact for a federal deployment is **the agency's own ATO and what boundary it already covers** — the dossier's compliance matrix says exactly this ("Agency ATO referencing the cloud provider's FedRAMP package") and the chapter's scenario drops it. The architect's first move is to inherit the existing authorized boundary, not to select one from a vendor table.
*Required fix:* separate three facts — (i) FedRAMP baseline is set by the agency's data categorization; (ii) DoD Impact Levels apply to DoD missions; (iii) the deliverable is an ATO over a boundary, and reclassification is the agency's call (the chapter gets *this* part right — keep it). Route the exact CUI→baseline mapping to the validator (see Validator questions Q1).

**[MAJOR] T7 — "Redacted/tokenized logging: GDPR/HIPAA exposure Low · Retention conflict Resolved — safe to retain longer" overstates what pseudonymization buys, and the discriminator explicitly describes a *reversible* token.**
The discriminator says "replaced with a reversible token under separate access control." A reversible token with a vault is pseudonymization, not anonymization; the data remains personal data and remains in scope for storage limitation, erasure, and breach notification. "Resolved — safe to retain longer" is a legal conclusion the chapter is not entitled to state.
*Counter-scenario:* an item asks what must still be true of tokenized logs under a DSAR/erasure request. A candidate taught "resolved" answers "nothing — they're tokenized." The correct answer is that the token→value mapping must be deletable, the retention period must still be bounded and documented, and the vault is itself a regulated store.
*Required fix:* split the column into **irreversible redaction/hashing** (materially reduces scope) vs. **reversible tokenization** (still personal data; the vault is a regulated store; retention and erasure obligations follow the token). Change "Resolved" to "Reduced, not eliminated — retention must still be bounded and the token map must be deletable."

**[MAJOR] §2.5 — processor/controller roles are stated as settled fact and silently assume the reader's organization is the controller.**
"Anthropic is processor on the 1P API…; the cloud provider is processor on Bedrock/Google Cloud" omits the customer's own role, which is contract-dependent. A very common case — a SaaS vendor building on Claude — makes the reader's org a *processor* for its own customers, which changes who answers a DSAR, who owes the DPIA, who notifies on breach, and whether the reader can even decide retention.
*Counter-scenario:* an item where a B2B SaaS team must support its enterprise customer's erasure request. A candidate who learned "we are the controller, Anthropic is our processor" designs the wrong flow and misses the key about back-to-back processor commitments and sub-processor disclosure.
*Required fix:* state the three-role chain explicitly and note that the reader's own role is set by contract, not by architecture. Add "who answers the DSAR" as the decision this concept drives.

**[MAJOR] §4 Scenario 2 "Changes the answer" — "genuine explicit consent or contract-necessity permits limited automation" is presented as an available lever without noting that both are contested in exactly this context.**
Consent obtained as a condition of a credit application sits badly with the freely-given requirement; contract necessity is narrowly construed. Presenting them as switchable levers drifts into legal advice and, on an item, invites a candidate to pick "obtain consent" as the fix for an Article 22 problem.
*Required fix:* frame as **"the statutory exceptions exist but their availability in consumer-credit contexts is contested; the architecturally safe answer keeps meaningful human involvement plus a contestability path regardless of which basis counsel asserts."*

**[MAJOR] §2.5 / Scenario 2 / Item 3 — the chapter never says the human involvement must be *meaningful*, which is where its own recommended answer is weakest.**
"Require a loan officer to finalize every recommendation" satisfies Article 22 only if the officer exercises real discretion with real capacity to disagree. A reviewer approving 300 recommendations a day is a rubber stamp, and the chapter itself names that failure mode in §5 and §6 without connecting it to Article 22.
*Counter-scenario:* an item where a human "confirms" every model recommendation but has no access to the underlying file and no throughput budget, and the options include "add meaningful review capacity and reviewer access to the underlying record" vs. "add a human confirmation step." A candidate taught "add a human" picks the weaker option.
*Required fix:* add the word **meaningful** and define it operationally: the reviewer has (a) access to the inputs, (b) authority to overrule, (c) throughput that permits actual consideration, (d) a measured override rate that is not ~0%. Route the precise legal authority to the validator (Q2).

**[MINOR] §2.5 / T6 — US-centric constructs presented as generic anonymization/minimization standards.**
"De-identification (Safe Harbor or Expert Determination)" is a HIPAA construct; removing the 18 HIPAA identifiers does not make a dataset anonymous under GDPR. T6's axis label "Minimization/minimum-necessary alignment" fuses two different legal tests (GDPR Art. 5 data minimization; HIPAA minimum necessary) into one row.
*Counter-scenario:* an item with EU personal data where an option claims data is "de-identified per Safe Harbor, so GDPR no longer applies." A candidate taught the fused framing accepts it.
*Required fix:* label each construct with its regime and state the one-line contrast: HIPAA de-identification is a defined-method safe harbor; GDPR anonymization is an outcome test (no reasonable means of re-identification) with no enumerated list.

**[NIT] §2.5 — "the 1P API is not itself a FedRAMP-authorized boundary" is correct but reads as permanent.** Add "as of the source date; authorization status is a moving target — verify per engagement," which the chapter already does for model rosters elsewhere.

### C. Vendor-flattering framing and dodged limitations

**[BLOCKER] §2.3 / §6 — the chapter never states the honest limitation that there is no complete defense against prompt injection, so it never teaches the architectural consequence.**
The dossier has the right framing verbatim ("reduces blast radius of a successful injection rather than trying to make injection impossible"). The chapter converts it into a tidy mitigation list that reads as closing the risk.
*Counter-scenario:* an item where all the listed mitigations are already in place and asks what most reduces residual risk. The key will be a blast-radius answer — remove the agent's write scope, run the untrusted-content step in a tool-free context, require a human to send, separate the reading identity from the acting identity. A candidate taught "isolate to tool_result and label provenance" picks a mitigation already present in the stem.
*Required fix:* state it as a first-class design premise — **"assume injection succeeds; design so that success is not consequential"** — and add the corollary to §2.3 and §7. This is also the fix for Item 6 (below).

**[MAJOR] §2.6 (explainability bullet) and Item 12 — the chapter's answer to "explainability" is a vendor feature plus caveats, which dodges the real limitation and skips the real architect move.**
Saying "citations show where, not why" is correct and good (keep it), but the chapter stops there. The honest statement is that LLM decision processes are not explainable in the reason-giving sense a consequential-decision regime expects, and the architectural consequence is that **the decision itself may need to come from an interpretable model or a deterministic rule set, with the LLM confined to summarizing, extracting, or drafting the explanation of a decision it did not make.** That option appears nowhere in the chapter — not in §2.6, not in T1, not in Scenario 2 or 5, not in any item.
*Counter-scenario:* an item where a lender must give applicants specific adverse-action reasons. The key is "score with the existing interpretable model; use Claude to draft the applicant-facing explanation from the model's reason codes." A candidate taught this chapter picks "add citations" or "add a human reviewer."
*Required fix:* add "don't use the LLM for the decision" as an explicit, named option in §2.6 and as a row in T1, and state that post-hoc rationales an LLM produces about its own output are not evidence of the process that produced it.

**[MAJOR] §2.5 / T5 / Scenario 1 — the "flagged content may be retained up to 2 years regardless of ZDR or a HIPAA arrangement" fact is in the dossier and dropped from the chapter.**
This is the single most important honest limitation for any erasure/retention discussion, and the omission is flattering by subtraction. It is also directly testable at architect altitude.
*Counter-scenario:* an item where a customer demands a contractual guarantee of complete erasure. The key is that trust-and-safety retention is an exception the architect must disclose and design around (don't send the data at all; pseudonymize upstream), not something ZDR resolves. A candidate taught "ZDR: Yes, by approval" answers "enable ZDR."
*Required fix:* restore the exclusion into §2.5 and T5 and make it a named anti-pattern ("ZDR-washing" alongside "BAA-washing").

**[MAJOR] §2.6 — presenting Anthropic's political even-handedness eval as "a worked example" for bias/fairness testing is both flattering and substantively misleading as a template.**
A paired-viewpoint, model-as-judge even-handedness eval measures *viewpoint* symmetry on a model. It is a poor template for disparate-impact review of a deployed lending, hiring, or claims system, where you need outcome-rate comparisons across segments in the deployed pipeline (retrieval coverage, thresholds, language handling), and where a model-as-judge scoring the thing under test has an obvious independence problem.
*Counter-scenario:* an item asking how to test a claims-triage system for disparate impact. A candidate templating on the even-handedness eval proposes paired prompts and an LLM judge; the key is segmented outcome-rate measurement on real or held-out decisions with a pre-declared fairness metric.
*Required fix:* keep the citation as an example of *eval discipline* (repeatable set, segmented, re-run on change) but explicitly say it is not the template for disparate-impact review, and give the actual one.

**[MINOR] §2.7 — "An AI review board typically owns…" is an unfalsifiable org-design assertion presented as standard practice.** It is untestable and consumes space a 14% domain needs. Either tie it to a decision ("who must approve an exception to the automated-decision policy") or cut it.

### D. Exam mismatch

**[MAJOR] §1 archetype 1 + §4 Scenario 4 + §7 heuristic 1 + §8 Item 1 teach the guide's own Domain 3 Sample 1 four times; §1 archetype 4 + §2.3 + §5 row 1 + §7 heuristic 5 teach the guide's Domain 4 Sample 3 four times.**
Both patterns are published, scored in *other* domains, and free to every candidate who read the guide. The chapter spends its most prominent real estate — the first archetype, a worked scenario, two heuristics, one item, one diagnostics row — re-teaching them. With ~9 scored items in this domain across 5 objectives, that is the largest opportunity cost in the chapter.
*Required fix:* keep each pattern once (heuristic + one diagnostics row), delete Scenario 4 and Item 1 or repoint them at the harder version (capability *is* needed → narrow authority), and spend the reclaimed space on the gaps in the next two findings.

**[BLOCKER] Objective 1 ("Implement guardrails and safety controls") gets a taxonomy and no implementation reasoning. The chapter gives a candidate nothing for the questions an exam will actually ask.**
Absent entirely: where the screen sits (pre-model input screen vs. post-model output screen vs. both, and why an output screen is mandatory for injection you cannot prevent); **fail-open vs. fail-closed when the guardrail service is unavailable** (a canonical architect item — and the answer differs by domain, matching T3's own cost-ratio logic); **streaming vs. buffered moderation** (you cannot retract a token you already streamed, so a streamed surface needs either buffering or a different control); the guardrail's own latency/cost budget and model choice; what happens when the guardrail is the single point of failure; and **how you know where the threshold should be** (T3 says set the operating point by the false-negative/false-positive cost ratio but never says you need a labeled harm set to locate it).
*Required fix:* add a subsection with those five decisions and their discriminators. Fail-open/fail-closed and streaming moderation alone are worth more exam-relevant reasoning than T5's entire FedRAMP table.

**[BLOCKER] No coverage of runtime authorization identity (the confused-deputy problem), and Scenario 7 sets it up and then fails to solve it.**
Scenario 7's situation says "servers run with the agent's privileges." The recommended answer (verified sources, sandboxing, monitoring) never addresses the privilege inheritance that makes the risk material. The governance question an exam will ask is whether the *end user's* authority or the *agent's service account* authority is used at the tool boundary. Every cross-tenant leak, every over-privileged retrieval, and every "the agent did something this user couldn't have done" incident is this problem.
*Counter-scenario:* an item where the agent's service account can read all tenants' records and the retrieval filter is applied in the prompt. The chapter's §2.3 does say "enforce tenant scoping at the data layer" — good — but never generalizes it to identity propagation, short-lived scoped credentials, or per-user token exchange, and never names the anti-pattern. A candidate will recognize the tenant case and miss the general one.
*Required fix:* add "whose authority does the tool call carry?" as a core concept with the three answers (agent service account / end-user delegated credential / per-tenant scoped credential), and fix Scenario 7's recommendation to lead with "the third-party server does not run with the agent's privileges."

**[MAJOR] Volatile specifics are given heuristic status.** §7 heuristic 7 asks the candidate to memorize the Bedrock-IL4/5-vs-Vertex-IL2 ceiling; T5 enumerates `inference_geo` values; §2.5 pins four EU AI Act dates including one the dossier itself marks partly `[UNVERIFIED]`; Item 2's rationale leans on an HTTP `400`; Item 4 is built entirely on the IL ceiling with the word "currently." The guide's own three sample items contain zero volatile specifics, and the credential is valid only 12 months — these facts will move inside that window.
*Required fix:* demote all of it to a single clearly-dated "verify per engagement" box, and keep only the durable statements as testable content: *FedRAMP/IL are properties of the deployment boundary, not the model; model-level authorization lags model release; residency on the 1P API is coarser than a regional hyperscaler endpoint.*

**[MAJOR] Objective 5 (ethics/bias/fairness) is the thinnest objective in the chapter and its two items are the two weakest, yet it will be scored.**
Nothing in the chapter gives a candidate the reasoning tools for the two most likely ethics items: (1) **removing a protected attribute does not remove disparate impact** — proxies and redundant encodings (zip code, school, device, language, name) carry it, so "we deleted gender from the prompt" is not a fairness control; (2) **fairness metrics are mutually incompatible** — you cannot simultaneously equalize error rates, outcome rates, and calibration across groups, so someone must *choose and document* the metric, and that choice is a governance decision, not a technical one. Also absent: the distinction between model-level bias and **system-level** disparate impact (thresholds, retrieval coverage, language support), which is where the architect's lever actually is.
*Required fix:* add both, plus one worked ethics scenario that turns on a proxy variable. This is where a rebuilt Item 10 should point.

**[MINOR] Under-covered governance surfaces the blueprint plausibly reaches:** multi-turn risk (per-turn guardrails miss slow escalation across a conversation); agent memory/persistent state as both a data-governance surface and an injection-persistence vector; the consumer Claude.ai / Teams surface being outside BAA scope (in the dossier, dropped from the chapter) and the shadow-AI governance question that follows; and AI-specific incident response mechanics beyond one sentence (who can roll back a prompt, is there a kill switch, notification duty).

### E. Hidden assumptions

**[MAJOR] T4's "Confidence-triggered" tier assumes calibrated confidence, and the chapter supplies no way to get it.**
T4 lists "High-volume, well-calibrated confidence" as the fit condition; §2.4's misconception bullet correctly notes models are confidently wrong. Nothing connects them. A model's self-reported confidence is not a calibrated probability.
*Counter-scenario:* an item offering "route outputs below a stated confidence threshold to a reviewer" against "escalate on retrieval-score floor, sample disagreement, out-of-distribution input, and an irreversibility flag." A candidate who read T4 picks the first.
*Required fix:* say plainly that self-reported confidence is not a usable trigger on its own, and enumerate the external signals that are (retrieval score, self-consistency across samples, novelty/OOD detection, validator failure, irreversibility flag, value threshold, anomaly). The chapter half-knows this — finish the thought in T4, not just in a §2.4 aside.

**[MAJOR] Reviewer availability, competence, and capacity are assumed throughout and never appear as a constraint.**
Scenario 5 silently assumes an insurer can staff human review of every denial. Scenario 2 assumes loan officers with real discretion. T4 costs the tiers in "Cost/latency" but never in "does a qualified reviewer exist within this action's latency budget, at this volume, at 3am."
*Required fix:* add reviewer capacity and coverage-hours as an explicit axis in T4, and add one "changes the answer" clause to Scenarios 2 and 5 where reviewer capacity is the binding constraint and the answer becomes tiering plus reversibility engineering.

**[MINOR] Other unstated assumptions to surface:** the reader's org is the controller (see B above); the deployment is a custom API application (nothing about Claude Code / Agent SDK / desktop surfaces); team maturity includes a review board, change management, and an eval gate (§2.7, Item 5); scale is single-region and single-jurisdiction; and "irreversible" is treated as a fixed property of an action rather than a design choice.

**[NIT] "Irreversible" is never defined.** Is sending an email irreversible? Scenario 4 treats "draft reply" as post-hoc-auditable, but a *sent* reply cannot be recalled. Supply the operational definition: *can the operator undo the effect, within the harm window, at acceptable cost, without the counterparty's cooperation?*

### F. Internal consistency and item-writing craft

**[MAJOR] §8 — in 6 of 12 items (2, 6, 9, 10, 11, 12) the key is the longest and most compound option; in items 10 and 12 it is roughly double every distractor.**
This is a testwiseness artifact. It trains a candidate to pick the longest option, which is precisely the habit a professionally item-written exam with balanced option lengths punishes. It also means several items can be answered without the content.
*Required fix:* balance option lengths within each item, and stop bundling two correct controls into one key (Items 5 and 11 both win by compounding).

**[MINOR] §9 objective-coverage table overstates coverage.** Objective 3 (HITL) claims Item 3, which is a GDPR-article item; Objective 2 (risks/failure modes) claims Item 12, which is a product-feature item. Objective 5 claims two items, both of which I rate defective/low-value. Map honestly so the editor sees the real gaps.

**[NIT] §2.3 lists ten failure modes as a flat bulleted set with no ordering by likelihood or blast radius.** For a triage reference, rank or group them (data-plane vs. action-plane vs. drift) — the diagnostics table in §5 does this well and §2.3 does not.

## Item-by-item adversarial re-solve

**Item 1 (agent with credit tool; remove it) — verdict: SOUND.**
Strongest alternative: C (lower the limit to $1,000), arguable only if "needed for the current use case" is read as temporary. The stem closes that off. The item is correct — but it is the guide's published Sample 1 with the nouns changed, and the chapter also teaches it as Scenario 4 and heuristic 1. *Fix:* keep at most one instance, and repoint the item at the version that actually discriminates: stem says the role *does* need credits up to $50, and the options contrast removal, a cap plus idempotency plus per-agent budget, a confirmation dialog, and logging. Key becomes the scoped-authority option — which also breaks the removal reflex the chapter over-installs.

**Item 2 (PHI summarization; BAA + HIPAA readiness + eligible features) — verdict: DEFECTIVE (wrong-reflex).**
The key is right; the item is not. All three distractors are free eliminations (subscription tier, a generic ZDR mention, "business hours and TLS"), so the item is answerable by keyword match: *PHI ⇒ pick the BAA option.* That is exactly the reflex that fails a well-written item, because a real item will put a BAA in three options and discriminate on something else. The chapter has the discriminating facts in its own dossier and uses none of them: the BAA does not cover the consumer Claude.ai product or the Teams tier; eligible-feature restriction is the part teams actually get wrong; and minimum-necessary/de-identification reduce exposure before any contract matters.
*Fix:* rewrite so every option includes a signed BAA and they differ on surface (consumer app vs. API workspace), feature eligibility, and whether PHI volume was minimized first. Also drop "required *first*" — the options are not temporally ordered, which makes the stem's superlative unanswerable as written.

**Item 3 (EU lender, fully automated denials; Article 22) — verdict: SOUND, weak distractors.**
No defensible second answer among the four (HIPAA and FedRAMP are free eliminations; Art. 5 is off-target for decision automation). Two real criticisms: (a) cognitive level is recall-with-a-scenario-wrapper, below the guide's samples; (b) the chapter teaches "EU + automated decision ⇒ Article 22" with no mention that consumer creditworthiness assessment is also a canonical EU AI Act high-risk use case. On a real item offering both regimes, this drill produces a premature Article 22 answer.
*Fix:* make two options plausible-and-different (Art. 22 vs. AI Act high-risk obligations) and ask which obligation the described design fails *first*, or ask what the design must add (meaningful human involvement + contestability), not which article is cited.

**Item 4 (CUI / IL4-5; B and C) — verdict: DEFECTIVE (volatile recall).**
A and D are absurd, so the item is a gimme for anyone who skimmed T5; it tests table recall, not judgment; and its key contains "currently tops out at IL2," which the dossier itself flags as a moving roster. An exam cannot fairly test this, and a candidate who memorizes it learns a fact with a ~12-month shelf life instead of the durable rule.
*Fix:* recast as a scenario whose key is the durable insight: the agency's ATO already covers Bedrock GovCloud, the team wants the newest Claude model, and the correct first action is to verify that *that model* is within the authorized roster — because authorization is boundary- and model-specific and lags release. That tests the same idea, survives roster churn, and requires reasoning.

**Item 5 (model upgrade shifted behavior; pin + regression eval) — verdict: UNDER-DETERMINED.**
The stem says "after a routine model version upgrade," which reads as an *intentional* upgrade. If it was intentional, "version-pin the model" is not the fix — the pre-promotion eval gate is, and B wins only because it bundles both. A candidate can defensibly argue the stem describes a floating alias auto-resolving to a new version (making pinning the fix) or an intentional promotion (making the eval gate the fix), and the stem does not say which. Additionally the strongest real control is absent: canary/staged rollout with an automatic rollback trigger.
*Fix:* state explicitly that the deployment references a floating "latest" alias; offer "pin the version" and "add a regression eval gate before promotion" as *separate* options plus "canary with rollback," and ask which most defensibly prevents *recurrence* — forcing a real ranking instead of rewarding the compound option.

**Item 6 (inbound email, indirect injection; tool_result + provenance label) — verdict: UNDER-DETERMINED (and mechanically off).**
Two attacks. (1) *Mechanics vs. stem:* the stem describes a pipeline that pre-fetches the email body and passes it to Claude. A `tool_result` block is a response to a model-initiated `tool_use`; a pre-fetching pipeline has no tool call to respond to, so a candidate who knows the message structure can reject B as not applicable to the described architecture and has nothing better to pick. Either the stem must have the model call a `get_email` tool, or the option must say "in a clearly delimited, provenance-labeled untrusted-content block, never in the system prompt." (Flagged to validator, Q3.) (2) *The dominant control is missing:* the chapter's own §2.3 lists "screen tool output before the model sees it" and least-privilege tool scope as indirect-injection mitigations, and neither appears among the options. For a draft-reply pipeline the real answer is that injection cannot achieve anything because the drafting step holds no tools and a human sends — blast-radius containment, not provenance labeling. As written the item under-determines what the harm even is (bad draft text that a human will read, vs. an unauthorized tool call).
*Fix:* say in the stem what the model can *do* after reading the email (if it can call tools, the key is scope removal plus output screening; if a human sends, say so and make the item about which control is redundant). Then Item 6 becomes the vehicle for the "assume injection succeeds" premise the chapter is missing.

**Item 7 (HITL tier pairing) — verdict: SOUND, below level.**
No defensible alternative — A and D let an irreversible transfer complete, B is transparently over-tiered. But it is a definitional matching item, not a scenario, and three options are eliminable without reading the stem. It also reinforces the gap in finding A4: the option that beats a synchronous gate in many real designs — automated execution inside a hard cap with a mandatory settlement delay and a self-service reversal window — is not offered.
*Fix:* make it a scenario with two defensible options (synchronous approval vs. automated-within-cap + delayed settlement + claw-back) and let the discriminator be whether the counterparty relationship makes reversal actually available.

**Item 8 (which two are OWASP LLM Top 10 categories) — verdict: DEFECTIVE. Delete.**
Three separate failures. (1) Pure recall trivia — the format the guide's samples explicitly avoid — and answerable by anyone who has never read OWASP, since "Insufficient Context Window" and "Slow Inference Latency" are obviously not security categories. (2) Blueprint drift: OWASP appears nowhere in the Domain 5 objectives; the brief's hard rule 1 forbids drifting into topics the blueprint does not measure, and a *recall* item on an unmeasured framework is the worst case of it. (3) The chapter is asking candidates to memorize a list its own dossier could not primary-verify (OWASP PDF 404; two secondary summaries only).
*Fix:* delete, and replace with a scenario applying the one OWASP idea that *is* on-blueprint — improper output handling: model output flows into a SQL query / shell command / rendered HTML, and the key is parameterization/encoding/sandboxing rather than a prompt instruction telling the model not to emit dangerous strings.

**Item 9 (GDPR vs. observability; redact/tokenize) — verdict: SOUND, rationale needs work.**
C is the best of the four. Two attacks on the teaching around it. (1) Per finding B/T7, C only *resolves* the tension if the redaction is irreversible; with a reversible token the logs remain personal data and retention/erasure obligations persist — a well-prepared candidate could argue C is incomplete, and the rationale's "resolves the tension directly" reinforces the overreach. (2) The rationale dismisses A ("disable all logging") as merely "sacrificing debuggability unnecessarily." For a high-risk system where record-keeping is independently mandated, disabling all logging is not a trade-off — it is a compliance failure. Saying so would teach the more valuable idea: logging is sometimes a *requirement*, which is the correct counterweight to the chapter's "logging is not a mitigation" drumbeat.
*Fix:* keep the item; rewrite the rationale on A and C along those lines, and make C's wording specify irreversible redaction for the sensitive payload with a bounded retention period.

**Item 10 (fairness checked once at launch; re-evaluate) — verdict: DEFECTIVE (strawmen, and the key is not the strongest critique).**
All three distractors are self-refuting ("bias evaluations are inherently unreliable," "absence of complaints proves fairness conclusively," "only relevant for consumer-facing products"). Worse, the key is not the best available critique of the described situation. Two stronger ones exist and are absent: (a) **the pre-launch eval may have measured the wrong thing** — it tested the model rather than the deployed system (retrieval coverage, thresholds, language handling), and was not segmented by the dimension of concern, so re-running it would just reproduce a non-measurement; (b) **"no complaints" is uninformative absent a channel** — if affected users have no feedback or appeal path, complaint volume measures the absence of a mechanism, not the absence of harm. A candidate who could construct either of those and finds only "re-run it" among the options is being trained down to the weakest true answer.
*Fix:* rebuild with four *defensible* critiques and ask for the strongest; key on the segmentation/deployed-system critique. Also add the proxy-variable item the chapter currently cannot support (finding D): "the team removed the applicant's gender field from the prompt — is the disparate-impact risk addressed?"

**Item 11 (hallucinated clause reached a client) — verdict: UNDER-DETERMINED.**
The stem asks what "most directly addresses the **root cause**," and names one root cause: output reached a client without review. The key bundles two controls, and the rationale itself concedes the operative half is the sign-off ("addressing the missing control that let an unreviewed output reach a client"). A candidate reasoning strictly about root cause can argue the quote-grounding half is a contributing-factor control, not the root-cause fix, and that a single-cause stem should have a single-cause key. Because B contains the right half, the item is unfalsifiable rather than instructive.
*Fix:* either split the options (sign-off gate / quote-grounding / both / neither) and keep "root cause," or change the stem to "most reduces the likelihood of recurrence" and make it select-2. Also consider offering the stronger structural answer: the client-delivery path cannot be reached from the drafting step at all — release requires a separate, authenticated action.

**Item 12 (what citations provide) — verdict: SOUND, low value.**
No defensible alternative; A/C are overstatements and D is transparently over-strong. But it is a product-feature recall item sitting under an *ethics* objective, its key is double the length of every distractor, and D ("equivalent to a formal explainability method required under the EU AI Act for all high-risk systems") cannot be reasoned about by a candidate using this chapter — the chapter never says what the AI Act actually requires, so D is eliminated by tone, not by knowledge.
*Fix:* keep one sentence of this content in §2.6 and replace the item with the explainability item the objective actually needs: a consequential-decision system must give specific reasons to the affected person, and the key is that the decision comes from an interpretable model/rule set with Claude drafting the explanation — with "add citations to the model's decision rationale" as the attractive, wrong option.

## Heuristic boundary conditions

| Heuristic as written (§7 / §3) | Required qualifier |
|---|---|
| "Remove the capability beats log/confirm/monitor **whenever removal is possible**." | …**whenever the role's actual task does not require the capability.** When it is required, the move is narrowing authority — scope, cap, rate, tenancy, credential lifetime — not removal and not logging. |
| "Detective controls never answer 'how do we prevent.'" | True for discrete actions. **Detection is the primary control for slow-onset risks** (drift, emergent disparate impact, index degradation, misuse of legitimate access) where there is no discrete action to gate — and **logging is independently mandated** in some regimes, so "add logging" is sometimes a requirement, not a distractor. |
| "A prompt instruction is never the complete answer for a material risk." | …never **sufficient on its own**. Where the constraint is fuzzy and admits no deterministic predicate, prompt + classifier + measured eval + blast-radius limits *is* the available answer; the correct option adds measurement and containment, not a replacement for the prompt. |
| "Irreversible + high-impact → synchronous human gate before execution." | **First make the action reversible** (staged/pending state, undo window, delayed settlement, soft delete, claw-back). Gate only the residue that cannot be made reversible, and only where a qualified reviewer is available within the action's latency budget at the expected volume. A gate with a ~0% override rate is a rubber stamp, not a control. |
| "Confident-but-wrong + document refresh + model/latency unchanged → retrieval." | Correct, and well-cued — **but this is the guide's Domain 4 sample**, scored there. Keep it once; do not let it occupy four places in a Domain 5 chapter. |
| "'Compliant because we use Claude' is always wrong." | **Vendor posture is necessary and never sufficient.** The correct option names both the vendor instrument (BAA/DPA/authorized boundary) and the customer-side obligation (minimization, oversight, retention, logging). |
| "FedRAMP High + IL4/5 → Bedrock GovCloud; IL2 → Vertex." | Replace with the durable rule: **FedRAMP baseline follows the agency's own data categorization; DoD Impact Levels apply to DoD missions; authorization attaches to a boundary *and* a model roster, and lags model release. Verify the current roster per engagement.** Keep the specific ceilings only in a dated "verify" box. |
| "Citations ground a claim; they don't explain the model's reasoning." | Correct — **and the architectural consequence is missing**: where a regime requires specific reasons for a decision, the decision may need to come from an interpretable model, with the LLM confined to drafting the explanation. A model's post-hoc rationale about its own output is not evidence of the process that produced it. |
| "Bias/fairness testing is recurring, not a one-time gate." | Correct, **but recurrence is worthless if the measurement is wrong**: the eval must test the *deployed system* (retrieval coverage, thresholds, language handling), be segmented by the dimension of concern, use a pre-declared fairness metric (the metrics are mutually incompatible — someone must choose), and account for proxies, since removing a protected attribute does not remove disparate impact. |
| T1: "A human gate whenever the action is irreversible or high-impact, **regardless of the other layers**." | Delete "regardless of the other layers." **A human gate is required when the decision contains judgment that cannot be reduced to a deterministic predicate.** When the action's parameters can be fully constrained in code, the deterministic control substitutes for the gate. |
| T3: "The operating point is set by the cost of a false negative relative to a false positive." | …**and you cannot locate it without a labeled harm set.** Add: decide fail-open vs. fail-closed for guardrail unavailability (domain-dependent, same cost ratio), and prefer graduated responses (warn / redact / clarify / downgrade / route to human) over a binary block. |
| T4: "Confidence-triggered … best for high-volume, well-calibrated confidence." | **Self-reported model confidence is not calibrated and is not a usable trigger alone.** Use external signals: retrieval score floor, self-consistency across samples, OOD/novelty detection, validator failure, irreversibility flag, value threshold, anomaly signal. |
| T6: "Set retrieval breadth by task need, then trim." | Add the mechanism, not just the posture: **tokenize or de-identify before retrieval, extract only the needed fields, and scope the index by purpose and tenant** so the minimization argument is structural rather than re-argued per request. |

## Must preserve

**Genuine strengths — do not lose these in editing.**

1. **The preventive / detective / compensating spine, and "logging is not a mitigation."** This is the correct organizing idea for the domain, it is exactly what the guide's own Sample 1 rationale rewards ("logging and confirmations are detective/compensating controls, not removal of unnecessary privilege"), and the §1 archetype 1 framing ("detective dressed as preventive") is the single most useful sentence in the chapter. Keep the distinction; just stop over-generalizing it (finding A).
2. **"Classify each *action*, not the whole system, by reversibility × impact" — and "one agent commonly needs different tiers per tool."** This is genuine architect altitude and is the chapter's best original contribution. T4's discriminator line and §2.4's decision statement should survive verbatim.
3. **The §2.3 failure-mode → *specific* mitigation mapping and the §5 symptom → first-thing-to-check table.** Both are shaped correctly for exam triage: they refuse the generic "test more" answer and name a distinct architectural response per failure mode. The §5 table in particular doubles as a usable reference and should not be prose-ified.
4. **The honest-limits sentences** scattered through the chapter: "grounding reduces (not eliminates) hallucination"; "regex redaction as a complete PII solution" as a named anti-pattern; "a prompt rule repeated three ways is still one layer"; "compensating controls only suffice when paired with accepted residual risk."
5. **"Reclassification belongs to the agency's data-classification authority, not the architect"** (Scenario 3) and the general habit of naming who owns a decision the architect does not own. That instinct is worth generalizing, not deleting.

**Correct but sounds wrong — do NOT "fix" these.**

- **"The 1P API is not itself a FedRAMP-authorized boundary."** Reads like a vendor knock in vendor-certification prep material. It is what the sources say and it is the load-bearing fact for any federal item. Keep it; only add "as of the source date."
- **"ZDR is a separate, partly-incompatible arrangement for certain models — not a substitute [for a BAA]"** (Item 2 rationale C). Reads like a nitpick. It is the actual trap: ZDR and a BAA solve different problems and, per the dossier, Covered Models require retention. Keep, and strengthen it with the flagged-content retention exception.
- **"Reliable de-identification of free-text dictation is itself unsolved"** (Scenario 1). Reads defeatist for prep material. It is honest, it is why option (c) loses, and it is the kind of limitation candidates must be taught rather than shielded from.
- **"Detective controls are always added for forensics and drift detection — never presented as the fix."** The "always/never" cadence looks like the absolutism I am attacking elsewhere. In this specific sentence both halves are right: you always add them, and they are never the answer to a prevention question.
- **T3's "a medical-dosing assistant should over-refuse"** sitting alongside §5's "spike in over-refusal complaints → guardrail strictness miscalibrated." These look contradictory and are not: the operating point is domain-dependent, which is the whole point of T3. An editor must not harmonize them into a single rule about refusals.
- **"Escalation should not trigger only on low model confidence — confidently wrong outputs exist."** Reads like it undercuts T4's own confidence-triggered tier. It does, correctly. The fix is to finish the thought in T4 (finding E), not to soften the §2.4 warning.
- **"Compliance is a property of the deployment configuration, never of the model alone."** Sounds like a slogan. It is the correct frame and it is the discriminator on every compliance item in the domain.
